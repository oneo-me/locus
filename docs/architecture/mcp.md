# Agent integration

The app coordinates read-only MCP discovery, explicit skill installation, and built-in terminal sessions. These are separate capabilities: enabling MCP does not launch an Agent. The desktop hosts the terminal; external Agent CLIs own authentication, model calls, permissions, and their own session semantics.

## Discovery and transport

`internal/discovery` uses the official Go MCP SDK and Streamable HTTP at `/mcp`. Each service captures one library root. It is disabled by default and always binds loopback at `127.0.0.1:<port>`, defaulting to port 2301. Settings exposes only the port, so other machines cannot reach the endpoint.

The service exposes only:

- `list_articles`: direct child notes and organizing directories; default limit 50, maximum 200; a numeric opaque-to-clients cursor returns the next page.
- `resolve_article`: visible note lookup by literal relative path or `locus://` address, optionally ending in `/index.md`.
- `search_articles`: case-insensitive substring matching over visible note paths, titles, summaries, and bodies; default limit 20, maximum 100, bounded body excerpts.

Responses identify navigation paths and real absolute file/directory paths. Organizing directories have no body file. Each call scans current content; MCP has no content-write tools, content-transfer service, or documentation Resources capability. Clients must have access to the returned local files and use their own tools to edit them. The bundled skill owns authoring guidance.

HTTP requests are bounded and protected against cross-origin browser requests. Host validation allows localhost and loopback addresses, rejecting arbitrary hostnames and unrelated IPs. SDK localhost protection remains enabled. There is no wildcard CORS policy. Stateless transport does not retain client sessions across calls. Disabling, changing the library, or applying connection settings closes the old listener before creating a new server. Failures appear in settings; listening is not described as running before bind succeeds.

## Skill installation

The desktop app resolves MyGo's resource directory and passes it to `internal/skills`, which reads the skill and references from `skills/locus/`. The source files live in `source/resources/skills/` and packer copies them into the app; they are not embedded in the executable. Missing resources fail installation rather than creating an empty skill. Installation explicitly targets the selected library or home directory's `.agents/skills/locus`. It creates a copy, not a source-tree-dependent symlink. Existing targets are refused, including earlier copies and symlinks; the user must move them before reinstalling. Redirected `.agents` or `skills` parents are rejected.

The installer stages resource files, reserves a previously absent destination, then moves entries into it. It does not claim a multi-file transaction: publication failures may leave an incomplete new directory and report its path for inspection. It never merges into an existing installation or cleans up other skill locations automatically. Moving the app does not invalidate installed copies; updates require explicit reinstallation.

## Built-in terminal

The titlebar terminal button, immediately left of More actions when that menu is present, opens a 600 × 500 logical-pixel Onevra Popover containing only the terminal view. It uses the same MyGo terminal component as Onevra’s terminal gallery, with a real PTY and the libghostty-vt emulator. Locus does not implement terminal rendering or a native bridge. Opening the popover initially starts the configured Agent through the selected shell in the library directory, only after explicit user activation; selecting None for Agent starts only the shell.

While a session is being created or its process is alive, the header button pulses with a repeating keyframe sequence: the icon warms toward the accent color and a rounded accent outline fades in and out. The pulse stops when creation fails, the process exits (including a failure that retains its output), or the session closes; Reduce Motion keeps the accent icon and outline without movement. The indicator therefore keeps a terminal that was left running behind a dismissed popover visible from any page.

The Agents settings category offers Default, zsh, bash, fish, sh, and PowerShell on Unix; Windows offers Default, PowerShell variants, and cmd. Agent choices include Codex, Claude Code, OpenCode, pi, Gemini CLI, and Aider. These programs must already be installed. Default shell-only sessions use MyGo’s platform shell discovery; Agent launches use the configured shell or the environment’s supported default shell. Unsupported defaults produce a visible error. Explicit shell launches resolve the executable before PTY creation, preferring PATH and then a matching absolute `SHELL` path. On macOS, lookup also checks standard Homebrew, MacPorts, and system binary directories so Finder launches can find installed shells even with a minimal PATH. Explicit paths remain authoritative; missing shells produce an error rather than switching to a different shell. Unix shells load interactive login configuration and invoke the Agent through the shell so aliases and functions are honored, then exit with its status. PowerShell and cmd run the Agent without retaining a shell after it exits. Library paths are passed as a working directory, never interpolated into shell commands.

Changing a selection in Settings saves a preference without executing it; the next terminal activation replaces the current session with the new selection. Successful exit (status 0) or interrupt exit (status 130) releases the terminal and closes the popover; reopening starts a new session. Other exit statuses retain the terminal and its output for diagnosis, including missing commands and PTY startup failures. Hiding and reopening a failed terminal retries. Ctrl+C is delivered to the program normally: it closes the popover only if the program actually exits, not when the Agent merely cancels a task. Reopening after a creation error retries. Hiding the popover via its button, Escape, outside click, or Settings retains the process and output. Switching libraries and quitting close the session. There is one session per window, with no persistence across restarts. The MyGo terminal handles process exit output, input, selection, copying, pasting, and resizing.

Native loading occurs off the UI thread. A generation guard disposes of late results after replacement, library changes, or shutdown. Exit notifications return to the UI thread and check session identity so a previous process cannot dismiss a replacement. Each session records its own exit, so the running indicator stops even when a nonzero status retains the terminal. The popover remains empty while loading; creation errors appear in its place, and reopening retries. The native emulator is bundled by Onevra’s packager through MyGo’s plugin manifest; direct Go runs may download it into MyGo’s cache on first use.

## Verification

Tests cover discovery paths, visibility of notes with legacy archive metadata, pagination, search, real MCP client/HTTP calls, tool inventory, and Host/Origin rejection. Installer tests verify copied content, existing-target preservation, and redirected-parent rejection. Isolated shell-function fixtures verify login-shell invocation and propagation of success, failure, and interrupt statuses without calling installed Agents. Terminal tests verify launch arguments, rejection of unknown commands, popover dimensions and dismissal, settings choices, header ordering, running-indicator state, stale asynchronous completions, and stale exit notifications without launching an Agent. An opt-in native test uses a connection fixture to render the actual terminal in light/dark themes, retain it across dismissal, close it on library change, and automatically dismiss the popover when the connection exits, without launching any shell or Agent. Additional native tests run a controlled shell fixture to verify that success and interrupt dismiss the terminal while nonzero failures preserve output; they never launch an Agent.

Permissions, actual shell and Agent interaction, selected-shell startup files, Windows PTYs, and client skill reloading require user acceptance. See [MCP access](../mcp.md) for client setup and [Development checks](../build.md#development-checks) for automated commands.
