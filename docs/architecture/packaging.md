# App packaging

Here, project root means the directory containing `packer.toml`. For Locus it is `source/`, selected with `--project source` from the repository root.

## Technology and responsibilities

`oneo-tool-packer` is a Rust 2024 CLI crate at `source/crates/oneo-tool-packer`, independent of GPUI. It inherits workspace version, edition, and dependencies and uses `source/Cargo.lock`. Serde, TOML, JSON, and plist handle standard metadata; anyhow retains error context and tempfile manages staging directories. Cargo.lock fixes dependencies. The tool does not implement its own TOML, JSON, or plist parsers. Locus's manually invoked release script builds on this CLI to create a universal macOS bundle, embed Sparkle, apply ad-hoc or optional Developer ID signing/notarization, and publish it; that product-specific mechanism is owned by [macOS releases and updates](updates.md).

`cli` owns arguments and target resolution; `config` owns validation and app identity; `cargo` reads metadata, invokes compilation, and consumes Cargo JSON artifact messages; `bundle` owns directories, resources, macOS icons/signing, and output replacement; `windows` owns PE architectures and DLL collection; `windows_env` discovers and loads Visual Studio C++ environments. dunce canonicalizes project paths, avoiding verbatim prefixes when ordinary Windows paths are available so dependency build scripts can join paths correctly. `launch` constructs the bundled executable command and owns foreground execution. The entry point orchestrates these steps.

## Inputs and builds

VS Code's shell build task runs `cargo run --locked -p oneo-tool-packer --` in `${workspaceFolder}/source`, using the repository tool. The dev task runs there too, adding `run` to build and launch a development bundle. Project tasks do not maintain separate PATH values or absolute tool paths; the shell must find Cargo and rustc. Windows users may run from ordinary PowerShell, CMD, or VS Code tasks, with the packager loading the required C++ environment automatically. `.vscode/tasks.json` is authoritative.

For separate installation, run `cargo install --path source/crates/oneo-tool-packer --locked` at the Locus root, ensure Cargo's bin directory is on PATH, and run `oneo-tool-packer --project source`. Project-root `packer.toml` requires `package`, `bin`, `name`, and `identifier`. macOS icons come from `icon.icon/`, and Info.plist is generated dynamically. Optional `output-directory` sets final output, defaulting to project-local `dist`; relative paths resolve from `--project`. Locus uses `../dist`, placing outputs in repository-root `dist/`. Optional top-level `resources` declares shared external files/directories. `[macos].resources` and `[windows].resources` add platform-specific resources. `[windows]` uses `runtime-directories` for DLL search paths and `runtime-files` for dynamically loaded DLLs. Locus configuration, icons, and resources live in `source/`. See `source/crates/oneo-tool-packer/src/config.rs` for field definitions. Unknown fields are errors.

`--project` defaults to the current directory. Without a subcommand the tool builds Release. `run` selects Cargo's development profile, appends ` Dev` to the configured app name and `.dev` to its identifier, packages through the same staging/resource/signing pipeline, and launches only after successful publication. There is no arbitrary profile-switch option. `--target` defaults to `rustc -vV`'s host in the project directory, overriding Cargo's default target. Supported targets are `aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-pc-windows-msvc`, and `aarch64-pc-windows-msvc`. The aliases `macos` and `windows` retain host architecture. Other targets are explicitly rejected.

The app package must be a workspace member containing the selected binary. `cargo metadata --no-deps --format-version 1` supplies its version. Cargo rustc JSON artifacts supply the executable's actual path, without guessing from directory names or text scans. Cargo resolves global/project `build.target-dir` and `CARGO_TARGET_DIR` according to its relative-path and precedence rules. Shared build directories work without duplicating configuration in `packer.toml`. Builds use `--locked` and explicit package, bin, and target; release packaging additionally uses `--release`. Project profiles still control strip, LTO, optimization, and panic policy.

macOS Release passes `-C link-arg=-Wl,-no_exported_symbols` only to the final main executable, not dependencies or Windows. Ordinary `cargo build --release` does not apply this packaging policy automatically. `--dry-run` only reads configuration/metadata and shows commands and destinations; it does not require target OS to match host and performs no build, signing, or launch. With `run`, it also previews the bundled executable command. Development macOS builds omit the release-only exported-symbol linker policy.

Windows MSVC builds set `target.<triple>.rustflags=["-C","target-feature=+crt-static"]` through Cargo `--config`, applying default static CRT policy to the entire target dependency tree rather than only the final binary. Explicit `RUSTFLAGS`, `CARGO_ENCODED_RUSTFLAGS`, or target-specific rustflags environment variables follow Cargo precedence and may override this default. Runtime collection still follows actual EXE/DLL dependencies; it does not assume all native libraries link statically.

## Platforms and outputs

Outputs use `<app name>[.app]` beneath the configured directory, with no platform or architecture subdirectories, and retain the configured official name and Bundle Identifier for release packaging; development runs use the suffixed identity. Locus ignores `/dist/` in Git. Cargo caches keep their target directories; changing target-dir does not change final output. Explicit-target builds and ordinary host builds have different caches, so the first explicit-target build compiles its dependencies.

Resource paths are project-relative or absolute. String entries copy under their original names. Entries such as `{ source = "tools/macos", destination = "tools" }` choose an output name, which must be one valid filename, excluding directory nesting and traversal. Directories copy recursively; duplicate names, non-regular files, and symlinks are errors. Shared `resources` copy to `.app/Contents/Resources` on macOS or the output's `resources` directory on Windows. Platform-specific resources then copy to that platform's same resource directory, without copying other platforms' entries. macOS resource copying precedes signing. Missing files or collisions prevent publication while preserving the old output.

macOS requires a Mac, Xcode, and Command Line Tools, with deployment target 13.0. Project-root `icon.icon/` is required and compiled with `actool --app-icon icon`. The tool generates Info.plist app name, identifier, executable name, version, minimum OS version, and native app fields, merging icon metadata. Projects do not maintain handwritten Info.plist files; macOS configuration declares only platform resources. Signing defaults to ad-hoc. `--codesign-identity` overrides `ONEO_PACKER_CODESIGN_IDENTITY`; Developer ID uses hardened runtime and a timestamp. Signing receives strict verification without notarization.

Windows requires Windows, Visual Studio C++ tools, and the Windows SDK, including linker, `rc`, and `dumpbin`. Other architectures also require corresponding Rust standard libraries and native dependency toolchains. If `dumpbin` or `rc` is unavailable, `vswhere` locates Visual Studio with C++ tools, the packager calls `VsDevCmd.bat` for the target architecture, parses its UTF-16 environment, and restarts itself as a subprocess using that environment. Only the packager and children receive it; system variables remain unchanged. Missing tools after loading produce an error without repeated restarts. Missing toolchains prompt installation of Desktop development with C++ and Windows SDK through Visual Studio Installer.

`dumpbin /dependents` recursively discovers static and delay-loaded imports, searching output directories, `runtime-directories`, and `VCToolsRedistDir/<arch>/*.CRT`. VC runtimes come from redistributable directories, not copies from development-machine System32. API sets and system libraries in system directories are not copied. Each EXE/DLL receives PE architecture validation; missing dependencies abort. Non-system DLLs loaded with LoadLibrary must be declared in `runtime-files` and also receive dependency checks. Project-root `icon.ico` is required; SDK `rc` compiles a temporary icon resource linked only into the selected main program. Missing icons or compilation failures abort before Cargo builds. The tool does not sign Windows executables.

The packager does not build across operating systems, install toolchains, or generate installers. Cross-architecture capability also depends on app dependencies. Interface references: [Cargo rustc](https://doc.rust-lang.org/cargo/commands/cargo-rustc.html), [DUMPBIN /DEPENDENTS](https://learn.microsoft.com/en-us/cpp/build/reference/dependents?view=msvc-170), and [Visual C++ runtime distribution](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files?view=msvc-170).

## Development execution

`run` executes the macOS bundle's `Contents/MacOS/<development app name>` or the Windows output's `<bin>.exe`, with the project root as working directory and inherited environment and standard streams. Arguments after `--` are forwarded without shell interpretation. On Unix, process replacement preserves signals and exit status; on Windows the tool waits and forwards the exit code. It does not use `open`, detach, or launch external terminals. Launch errors leave the successfully packaged output in place. Quit existing development instances before rebuilding; the tool does not stop them or provide hot reload.

The development identity separates bundle publication and OS identity, not application-owned storage. Locus retains its existing settings, caches, library, and MCP port, and ordinary local bundles have no updater.

## Failure handling and verification

The app is assembled, checked, and signed in a temporary directory on the output filesystem. A file lock serializes publication, and successful completion replaces the whole output. Replacement failure restores the old directory. If restoration also fails, staging remains and the recovery location is reported. Build, signing, resource, or DLL failures do not delete old outputs.

Run `cargo fmt --all --check`, `cargo clippy -p oneo-tool-packer --all-targets --locked -- -D warnings`, and `cargo test -p oneo-tool-packer --all-targets --locked`. Tests cover target resolution, dedicated link arguments, artifact selection, recursive DLLs and architectures, resource collisions, publication recovery, and CLI contracts using simulated compilers on Unix.

Check shared build directories using global relative configuration, project relative configuration, and environment variables, verifying the actual executable path and packaging destination. Repository-root `--dry-run` must read `source/packer.toml` and target `dist/Locus.app`. None of the four supported targets adds platform or architecture subdirectories.

Real macOS bundles require checks of plist, exported symbols, resources, and signing. Native Windows builds, runtime completeness, and startup require Windows verification. Simulated tools, resource-copy tests, and dry runs do not count as target-platform acceptance.

Locus copies `source/resources/skills` as shared resources to `Contents/Resources/skills` on macOS and `resources/skills` on Windows, including the skill entry point and task-specific references. Settings installs a directory symlink to app resources; see [Agent integration](mcp.md#skill-distribution-and-installation).
